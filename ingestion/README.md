# GeoLogic Monitor Ingestion

Ingestion загружает инфраструктуру и городские события, передаёт постоянные данные в API, отслеживает изменения рядом с пользовательскими точками и публикует задания на уведомления в Kafka. Собственная PostgreSQL используется только для временного кэша мониторинга конкурентов; постоянными продуктовыми данными владеет API.

## Место в системе

```text
городские API ─┐
Overpass ──────┼─→ ingestion ──HTTP──→ API ──→ PostgreSQL/PostGIS
справочник ────┘       │          ↑
                       ├── 2ГИС ───┘
                       └── Kafka ──→ bot ──→ MAX
```

Ingestion взаимодействует с API через `/internal/v1`, подписывая запросы `INGESTION_SERVICE_TOKEN`. Пешеходные расстояния также запрашиваются через API, который централизованно управляет OSRM.

## Источники данных

| Источник | Использование | Доступ и обновление |
| --- | --- | --- |
| `spb-classif.gate.petersburg.ru` | Вокзалы, рестораны, гостиницы, музеи, выставочные залы, театры, аптеки, кинотеатры и ветеринарные клиники | Открытые городские наборы; ingestion запрашивает их по расписанию `SCHEDULER_INFRA_CRON` |
| `egs.gate.petersburg.ru` | Городские мероприятия и уличные выступления | Открытые данные; ingestion обновляет события по `SCHEDULER_EVENTS_CRON` |
| `yazzh.gate.petersburg.ru` | Детские и досуговые площадки | Открытые городские данные; обновление входит в инфраструктурный job |
| `maps.mail.ru/osm/tools/overpass/api` | Коммерческие и сервисные объекты OpenStreetMap | Overpass API без ключа; категории сопоставляются со справочником типов инфраструктуры |
| 2ГИС Catalog API | Поиск новых прямых конкурентов рядом с отслеживаемыми точками | Требует `TWOGIS_API_KEY`; мониторинг выполняется по `SCHEDULER_COMPETITORS_CRON` |
| `static/subway.json` | Станции и входы метро Санкт-Петербурга | Версионируемый подготовленный справочник; загружается вместе с остальной инфраструктурой |
| DaData Suggest и GeoLocate | Получение координат для записей с адресом и обратное геокодирование | Ingestion обращается к внутреннему API GeoLogic; ключ DaData хранится только в окружении API |
| OSM PBF `RU-SPE.pbf` | Исходные дорожные данные для пешеходной маршрутизации | Используется OSRM; ingestion получает расстояния через внутренний HTTP-метод API |

Рабочий сценарий использует реальные внешние источники. Статическим подготовленным набором является только `static/subway.json`. Примеры объектов в OpenAPI и DATA-API являются тестовыми и не подменяют интеграции.

## Обработка данных

1. При старте ingestion синхронизирует справочник типов инфраструктуры и типов бизнеса с API.
2. Инфраструктурный job получает наборы из городских API, статического справочника и Overpass, нормализует координаты и выполняет идемпотентный upsert через API.
3. Event job получает актуальные мероприятия и сохраняет их через API с парой `provider + external_id` в качестве устойчивого внешнего ключа.
4. Мониторинг получает пользовательские точки из API, проверяет 2ГИС на появление прямых конкурентов и сопоставляет ближайшие события.
5. Для подходящих изменений ingestion рассчитывает пешеходное расстояние через API и публикует типизированное сообщение в Kafka topic `notifications`.
6. Bot получает сообщение и доставляет его в зарегистрированный личный чат MAX.

Повторная загрузка одного и того же внешнего объекта обновляет существующую запись. Временные ошибки источников повторяются согласно HTTP-конфигурации; исчерпание попыток завершает текущий запуск dataset с ошибкой, не удаляя ранее сохранённые данные. Следующий запуск по расписанию повторяет синхронизацию.

## Конфигурация

Создайте локальный файл окружения:

```bash
cp ingestion/.env.example ingestion/.env
```

| Переменная | Назначение |
| --- | --- |
| `POSTGRES_HOST`, `POSTGRES_PORT`, `POSTGRES_USER`, `POSTGRES_PASSWORD`, `POSTGRES_DB` | Временный кэш ingestion |
| `KAFKA_ADDRESSES` | Адреса Kafka brokers |
| `GEO_API_URL` | Базовый URL GeoLogic API |
| `INGESTION_SERVICE_TOKEN` | Bearer-токен внутренних методов API |
| `TWOGIS_API_KEY` | Ключ 2ГИС Catalog API |
| `SCHEDULER_INFRA_CRON` | Расписание обновления инфраструктуры |
| `SCHEDULER_EVENTS_CRON` | Расписание обновления событий |
| `SCHEDULER_COMPETITORS_CRON` | Расписание мониторинга новых конкурентов |
| `SCHEDULER_EVENT_NOTIFICATIONS_CRON` | Расписание публикации уведомлений о событиях |
| `LOG_LEVEL`, `LOG_FORMAT` | Параметры журналирования |

Адреса источников, ограничения HTTP-клиентов, категории, веса, радиусы и параметры Kafka находятся в [`config.yml`](config.yml).

## Запуск

Из корня репозитория:

```bash
cp .env.example .env
cp api/.env.example api/.env
cp ingestion/.env.example ingestion/.env
docker compose up --build -d postgres kafka osrm api ingestion
docker compose logs -f ingestion
```

В составе полного решения используется одна команда:

```bash
docker compose up --build -d
```

## Проверка

```bash
cd ingestion
go test ./...
```

Работу загрузчиков и мониторинга проверяют по структурированным журналам ingestion, созданным объектам внутренних методов API и сообщениям topic `notifications` в Kafka UI на <http://localhost:8088/>.

## Границы решения

- источники и правила категорий настроены для Санкт-Петербурга;
- доступность и полнота данных определяются внешними поставщиками;
- временный кэш конкурентов не является историей уведомлений и может быть восстановлен повторным мониторингом;
- доставка через Kafka имеет семантику как минимум один раз, поэтому downstream-компоненты допускают повторную обработку сообщения.
