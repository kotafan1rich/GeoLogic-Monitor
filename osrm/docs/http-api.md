# Использование OSRM HTTP API

В проекте OSRM работает с графом, подготовленным профилем `foot.lua`, поэтому все запросы рассчитывают пешеходные маршруты. API использует два endpoint: `route` для одного маршрута и `table` для пакетного расчёта расстояний рейтинга и ingestion. Ingestion не вызывает OSRM напрямую: он использует защищённый метод API `POST /internal/v1/routes/walking-distances`.

## Адрес сервера

Из контейнеров сети `geo_logic_net`:

```text
http://osrm:5000
```

С хоста:

```text
http://localhost:<OSRM_HTTP_PORT>
```

`OSRM_HTTP_PORT` задаётся в корневом `.env`. Внутренний порт контейнера всегда равен `5000`.

## Общий формат запроса

```text
GET /{service}/v1/foot/{longitude},{latitude};{longitude},{latitude}?{parameters}
```

Координаты:

- передаются в порядке `longitude,latitude`, а не `latitude,longitude`;
- разделяются точкой с запятой;
- должны попадать в область загруженной карты Санкт-Петербурга;
- привязываются OSRM к ближайшему доступному сегменту пешеходного графа.

URL в shell нужно заключать в кавычки, иначе `;` и `&` будут интерпретированы оболочкой.

## Route API

Route API рассчитывает маршрут между двумя или несколькими точками.

```text
GET /route/v1/foot/{coordinates}
```

Обязательны только координаты минимум двух точек. Для проверки доступности маршрута геометрия и пошаговые инструкции не нужны, поэтому рекомендуется передавать `overview=false`.

Пример:

```bash
curl 'http://localhost:5000/route/v1/foot/30.315868,59.939095;30.335098,59.934280?overview=false'
```

Используемые параметры:

| Параметр | Значение | Назначение |
| --- | --- | --- |
| `overview` | `false` | Не возвращать геометрию всего маршрута. |
| `steps` | `true` или `false` | Возвращать или не возвращать пошаговые инструкции. Для рейтинга не требуется. |
| `alternatives` | `true` или `false` | Запрашивать альтернативные маршруты. Для рейтинга не требуется. |
| `radiuses` | Радиус для каждой координаты в метрах | Ограничить расстояние привязки координаты к графу. Значения разделяются `;`. |
| `hints` | Hint для каждой координаты | Повторно использовать ранее выполненную привязку к графу. |

Минимально значимые поля ответа:

```json
{
  "code": "Ok",
  "routes": [
    {
      "distance": 1557.6,
      "duration": 1121.5
    }
  ],
  "waypoints": [
    {
      "location": [30.315203, 59.939551],
      "distance": 62.96,
      "hint": "..."
    }
  ]
}
```

- `routes[].distance` — длина маршрута в метрах;
- `routes[].duration` — расчётная продолжительность в секундах;
- `waypoints[].location` — координаты после привязки к графу;
- `waypoints[].distance` — расстояние от исходной координаты до привязанной точки;
- `waypoints[].hint` — внутренний идентификатор привязки, пригодный для повторного запроса на том же графе.

Hint не требуется сохранять для однократного расчёта рейтинга. После обновления графа старые hints могут стать недействительными.

## Table API

Table API: один запрос получает пешеходные расстояния от создаваемой точки до нескольких объектов инфраструктуры.

```text
GET /table/v1/foot/{coordinates}?sources=0&destinations=1;2;...&annotations=distance
```

Индексы относятся к порядку координат в URL:

- координата `0` — исходная точка;
- координаты `1..N` — объекты инфраструктуры;
- `sources=0` выбирает только исходную точку;
- `destinations=1;2;...` выбирает объекты назначения;
- `annotations=distance` запрашивает расстояния в метрах.

Пример для одной исходной точки и двух объектов:

```bash
curl 'http://localhost:5000/table/v1/foot/30.315868,59.939095;30.335098,59.934280;30.327000,59.936000?sources=0&destinations=1;2&annotations=distance&skip_waypoints=true'
```

Основные параметры:

| Параметр | Требование | Назначение |
| --- | --- | --- |
| `sources` | Для рейтинга: `0` | Индексы исходных точек. |
| `destinations` | Для рейтинга: `1..N` | Индексы объектов назначения. |
| `annotations` | Для рейтинга: `distance` | Вернуть матрицу расстояний в метрах. |
| `skip_waypoints` | Опционально: `true` | Не возвращать описания привязанных source/destination points. |
| `radiuses` | Опционально | Ограничить привязку каждой координаты к графу. |
| `hints` | Опционально | Повторно использовать известные привязки координат. |

Пример ответа:

```json
{
  "code": "Ok",
  "distances": [
    [1557.6, 1117.7]
  ]
}
```

`distances[0][i]` соответствует `i`-му destination из параметра `destinations`. Если отдельный маршрут не найден, соответствующее значение будет `null`. Такой объект нужно пропустить; заменять `null` прямым расстоянием нельзя.

По умолчанию сервер принимает максимум 100 координат в одном Table-запросе. При одной исходной точке это не более 99 объектов. Внутренний HTTP-контракт API поэтому принимает от 1 до 99 destinations; больший список ingestion разбивает на пакеты.

## Обработка ошибок

Клиент должен проверять одновременно HTTP status, возможность разобрать JSON и поле `code` в ответе OSRM.

Основные результаты:

| Результат | Обработка |
| --- | --- |
| `code: Ok` | Использовать маршрут или матрицу. |
| `code: NoRoute` | Маршрут Route API не найден. |
| `code: NoTable` | Матрица Table API не может быть построена. |
| `null` внутри `distances` | Не найден только конкретный маршрут; пропустить соответствующий объект. |
| `InvalidQuery` или `InvalidUrl` | Ошибка формирования запроса. |
| `TooBig` | Превышен лимит координат; уменьшить пакет. |
| Timeout, HTTP 5xx или некорректный JSON | Считать OSRM недоступным и завершить обязательный расчёт рейтинга ошибкой. |

Не следует использовать прямое расстояние как незаметный fallback для пешеходного: это изменит смысл рейтинга.

## Рекомендации для API-клиента OSRM

- Использовать внутренний адрес `http://osrm:5000`, а не опубликованный host port.
- Задавать HTTP timeout; рекомендуемое начальное значение — `5s`.
- Передавать исходную точку первой координатой.
- Запрашивать только `annotations=distance` и `skip_waypoints=true`, если сведения о привязке не нужны.
- Делить кандидатов на пакеты меньше серверного лимита.
- Не логировать полные ответы для больших таблиц.
- После ответа сопоставлять элементы `distances` с объектами в том же порядке, в котором они были переданы.

Полное описание параметров находится в [официальной документации OSRM HTTP API](https://project-osrm.org/docs/v26.4.0/http).
