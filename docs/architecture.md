# Архитектура

Целевая архитектура хакатонного MVP: три независимых Go-модуля со своими go.mod, go.sum, Dockerfile, конфигурацией и DI. Общего Go-пакета и импортов соседних модулей нет. В API уже реализованы история рейтинга, доступ Mini App и планировщик.

OSRM — отдельный инфраструктурный контейнер, а не четвёртый Go-модуль. Его образ и подготовка локального графа находятся в каталоге `osrm`.

## Ответственность модулей

| Модуль | Ответственность | Доступ к данным |
| --- | --- | --- |
| api | Пользователи, точки, геокодинг, справочники, инфраструктура, события и история рейтинга, авторизация Mini App; плановый пересчёт | Собственная PostgreSQL через pgxpool; DaData Suggest для прямого и обратного геокодинга; OSRM для рейтинга и внутренних запросов расстояний |
| ingestion | Загрузка источников, мониторинг изменений и публикация сигналов | Постоянные данные через внутренний API; отдельная PostgreSQL для кэша 2ГИС |
| bot | Webhook MAX и технический /start; целевые Kafka consumer и отправка оповещений | HTTP API; после реализации уведомлений — Kafka; без БД |

API владеет постоянными данными. Ingestion сначала загружает InfraType, затем BusinessType/InfraObject, затем Event. Загрузка выполняется через внутренние HTTP-методы. Кэш 2ГИС остаётся локальной ответственностью ingestion и хранится в отдельной БД без внешних ключей к БД API. Каждый модуль применяет только собственные миграции.

При добавлении точки API грубо отбирает инфраструктуру через PostGIS, уточняет пешеходные расстояния через OSRM и рассчитывает рейтинг. Создание точки и первый рейтинг сохраняются атомарно: при недоступности OSRM или общей ошибке расчёта точка не сохраняется. Планировщик внутри API последовательно пересчитывает все точки той же логикой и добавляет успешные результаты в историю. Поведение описано в [расчёте рейтинга](impact-engine.md).

В текущей реализации bot принимает webhook MAX: `/start` регистрирует чат и предлагает открыть Mini App. Целевая архитектура добавляет в тот же процесс Kafka consumer и отдельный обработчик отправки уведомлений. Остановка consumer после ошибки не должна блокировать обработку webhook; ошибка должна быть видна в логах.

## Слои и каталоги

Зависимости: `cmd → app/DI → handler → service → repository`. Слои взаимодействуют через интерфейсы, зависимости собираются вручную в app/di.go. Domain не зависит от HTTP, pgx и Kafka. DTO обработчиков — в handler/.../dto; специфичные структуры адаптеров — в repository/.../model. Генератор Go-кода пока не выбирается.

Ниже приведена целевая структура; отдельные компоненты `bot` и `ingestion` ещё не реализованы полностью.

## Локальная инфраструктура OSRM

Compose собирает OSRM из закреплённого образа `ghcr.io/project-osrm/osrm-backend:v26.9.0-debian`. При сборке образ использует локальный `osrm/data/SanktPetersburg.osm.pbf`, а при его отсутствии автоматически скачивает городскую выгрузку Санкт-Петербурга с BBBike. Исходный файл сохраняется в образе как `/source/SanktPetersburg.osm.pbf`, подготовленный MLD-граф — в volume `osrm_graph`. Для маршрутизации используется профиль `/opt/foot.lua`.

Внутри сети `geo_logic_net` сервис доступен по адресу `http://osrm:5000`. Порт хоста настраивается переменной `OSRM_HTTP_PORT` и по умолчанию равен `5000`. Инструкции по сборке, обновлению карты и проверочным запросам находятся в [README OSRM](../osrm/README.md); общая настройка окружения — в [инструкции по локальной разработке](local-development.md).

## Мониторинг и загрузка

Ingestion получает через API снимок точек и необработанные события рядом с ними. Данные инфраструктуры и событий заполняются адаптером загрузки, основанным на старом проекте; для повторных запусков используются идемпотентные PUT. OSM служит источником графа OSRM. Локальная версия прежнего ingestion содержит заготовки, поэтому готовая совместимость не предполагается: JSON адаптеров сверяется с новым OpenAPI.

Ежедневный запуск ищет конкурентов за вчера и события на завтра по Europe/Moscow. Ingestion запрашивает у API пакет пешеходных расстояний от одной точки до 1–99 целей через `POST /internal/v1/routes/walking-distances`; только API обращается к OSRM. Отдельный `null` в ответе означает, что маршрут до этой цели не найден; такой кандидат пропускается. Ingestion не собирает признаки и не рассчитывает рейтинг. Данные 2ГИС не копируются в постоянную таблицу инфраструктуры.

Для события сначала публикуются сообщения для всех подходящих точек, затем через API устанавливается отметка обработки. Точка из снимка может быть удалена во время запуска и получить последнее сообщение.

## Контракты и доступ

[OpenAPI](../api/docs/openapi.yaml) описывает пользовательские и внутренние методы; [AsyncAPI](asyncapi/notifications.yaml) — задания на отправку. При реализации нового контракта обновляются локальные DTO производителей и потребителей и примеры; общий модуль моделей не вводится.

Mini App — браузерный интерфейс внутри MAX: добавление, просмотр и удаление точек, текущий рейтинг и история. Он обращается напрямую к пользовательским HTTP-методам API. Frontend реализован в `miniapp` на React, TypeScript и Vite и в production публикуется через Caddy; четвёртый Go-модуль не вводится.

### Авторизация Mini App через initData

При каждом запуске Mini App клиент MAX формирует `window.WebApp.initData`. Это URL-кодированная строка параметров, которая содержит сведения о запуске, включая `user`, `auth_date` и `hash`. Поле `user` содержит MAX user ID, `auth_date` — Unix timestamp формирования данных, а `hash` — подпись остальных параметров. Набор может также включать `query_id`, `chat`, `ip` и `start_param`.

Mini App передаёт исходную строку без разбора и повторного кодирования в заголовке:

```http
X-Max-Init-Data: <window.WebApp.initData>
```

Объект `window.WebApp.initDataUnsafe` может использоваться интерфейсом для отображения данных, но не является доказательством личности пользователя. API не принимает MAX user ID отдельным пользовательским заголовком и не доверяет полям `user` до проверки подписи.

API выполняет проверку по [официальному алгоритму MAX](https://dev.max.ru/docs/webapps/validation):

1. Разбирает initData как набор URL-кодированных пар `key=value` и отклоняет пустые данные, ошибки кодирования и повторяющиеся параметры.
2. Требует единственный `hash`, сохраняет его и исключает из подписываемого набора.
3. URL-декодирует значения, сортирует остальные параметры по имени и объединяет их через перевод строки в `key=value\nkey=value`.
4. Вычисляет секретный ключ как `HMAC-SHA256`, где ключ — строка `WebAppData`, а данные — `MAX_BOT_TOKEN`.
5. Вычисляет ожидаемую подпись подготовленных параметров через `HMAC-SHA256` с секретным ключом из предыдущего шага.
6. Сравнивает полученную подпись с `hash` безопасным сравнением, не зависящим от времени совпадения префикса.
7. Проверяет `auth_date`: значение должно быть положительным, не находиться в будущем и быть не старше `MINIAPP_INIT_DATA_MAX_AGE` (по умолчанию один час).
8. Декодирует `user` и принимает `user.id` только после успешного завершения всех предыдущих проверок. Идентификатор должен быть положительным.

Проверенный `user.id` помещается middleware в context запроса. Handler получает пользователя через сервис API и использует его внутренний UUID при операциях с точками. Поэтому подмена `user.id`, `auth_date` или любого другого подписанного параметра делает подпись недействительной. Просроченные, повреждённые и неподписанные данные возвращают `401 Unauthorized`; причина проверки клиенту не раскрывается.

Для проверки используется серверный `MAX_BOT_TOKEN` того бота, которому принадлежит Mini App. Он отличается от `BOT_SERVICE_TOKEN` и `INGESTION_SERVICE_TOKEN`, никогда не передаётся в Mini App и не используется как Bearer-токен пользовательского запроса. Исходные initData, подписи и токены не логируются. Пользовательские запросы в production идут по HTTPS; при разных origin API разрешает CORS только для настроенного origin Mini App.

Bot использует BOT_SERVICE_TOKEN и X-Max-User-Id из проверенного обновления MAX только для `PUT /api/v1/users/me`: `/start` регистрирует личный чат уведомлений. Mini App не может произвольно задать адресата уведомлений и предлагает запустить бота, если пользователь ещё не зарегистрирован. Заголовок X-Max-User-Id сам по себе не авторизует. Ingestion использует отдельный INGESTION_SERVICE_TOKEN; токены не взаимозаменяемы. API проверяет владельца точки. Секреты и сырые ответы 2ГИС не логируются.

## Kafka и ошибки

Kafka-контракт и брокерная конфигурация определены, но producer в ingestion и consumer в bot пока не реализованы. Целевая схема использует один topic notifications, одну partition для демо, group bot-notifications и franz-go на producer и consumer. Retention — один час; удаление сегментов Kafka асинхронное. Bot должен подтверждать offset после успешной отправки MAX. Предусмотрены три попытки с паузами 1, 2, 4 секунды; после исчерпания попыток consumer останавливается с ошибкой без commit. Некорректное сообщение также требует вмешательства оператора.

Outbox, DLQ и распределённой транзакции нет: при сбоях возможны дубли и пропуски. Публикация в Kafka не означает доставку или прочтение MAX. Детали отметок и TTL находятся только в [модели данных](data-model.md).

Ошибка отдельной точки не прерывает обработку остальных. Ответ `null` для отдельной цели пропускает только этого кандидата; прямое расстояние не показывается как пешее. Общая ошибка OSRM во время мониторинга возвращается ingestion как `503 provider_unavailable`, после чего пакет кандидатов пропускается. Недоступность OSRM во время создания точки приводит к 503 и откату создания. Catch-up пропущенных дней и одновременные запуски ingestion в MVP не поддерживаются.
