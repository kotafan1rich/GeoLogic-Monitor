# Локальная разработка

Проект использует Docker Compose для инфраструктуры и Taskfile как короткий интерфейс к основным командам. Три приложения находятся в независимых Go-модулях `api`, `ingestion` и `bot`; команды Go нужно запускать из каталога соответствующего модуля.

## Требования

- Docker с поддержкой Compose;
- Go 1.27 для запуска и проверки модулей без Docker;
- [Task](https://taskfile.dev/docs/installation) — необязательно, все команды можно выполнить напрямую через `docker compose`.

## Переменные окружения

Docker Compose ожидает отдельный env-файл для каждого приложения. Создайте локальные файлы из шаблонов:

```bash
cp api/.env.template api/.env
cp ingestion/.env.template ingestion/.env
cp bot/.env.template bot/.env
cp .env.template .env
```

Файлы `.env` не коммитятся. Шаблоны модулей содержат их текущие настройки, включая адреса внешних сервисов и значения-заглушки для секретов. Корневой `.env` управляет опубликованными портами и изменяемыми параметрами локальной инфраструктуры:

```dotenv
OSRM_HTTP_PORT=5000
KAFKA_HOST_PORT=9092
KAFKA_RETENTION_MS=3600000
```

Внутри сети Compose API обращается к маршрутизатору по адресу `http://osrm:5000`; ingestion получает пешеходные расстояния через внутренний HTTP-метод API. `OSRM_HTTP_PORT` меняет только порт OSRM на хосте. Kafka доступна контейнерам по адресу `kafka:19092`, а `KAFKA_HOST_PORT` меняет только её порт на хосте. Production Compose принимает `KAFKA_RETENTION_MS` через deploy env и не публикует Kafka наружу; без переменной используется значение по умолчанию `3600000`.

PBF-выгрузка карты не коммитится. При сборке OSRM городская выгрузка Санкт-Петербурга автоматически скачивается с BBBike, если файл `osrm/data/SanktPetersburg.osm.pbf` отсутствует. При необходимости автоматическую загрузку можно пропустить, заранее поместив совместимый файл по этому пути. Подробности описаны в [инструкции OSRM](../osrm/README.md).

## Текущее состояние запуска

Все три Go-модуля имеют исполняемые файлы, Dockerfile и env-шаблоны. Bot обрабатывает webhook MAX и сценарий `/start`, ingestion загружает данные по расписанию, Mini App имеет отдельную frontend-сборку. Kafka producer в ingestion и consumer уведомлений в bot пока не реализованы, поэтому полный сценарий доставки уведомлений через Kafka не завершён.

Локальный OSRM собирается и запускается независимо: при первом старте entrypoint подготавливает пешеходный граф, проверяет его и сохраняет в volume `osrm_graph`.

Собрать и запустить OSRM:

```bash
docker compose up --build -d osrm
```

После первой сборки для него определены команды запуска и остановки через Taskfile:

```bash
task osrm:up
task osrm:down
```

Подготовка пешеходного графа при первом запуске требует до 1 ГБ оперативной памяти. Состояние подготовки и сервера видно в журнале:

```bash
docker compose logs -f osrm
```

Подробности о данных, volume и HTTP-запросах приведены в [инструкции OSRM](../osrm/README.md).

## Базы данных

Для целевого стека определены две независимые PostgreSQL/PostGIS:

```bash
task api-db:up
task ingestion-db:up
# или обе сразу
task db:up
```

API использует порт `5432` хоста, ingestion — `5433`. Данные сохраняются в volumes `api_db_data` и `ingestion_db_data`.

Обычная остановка сохраняет данные:

```bash
task db:down
```

`docker compose down -v` удаляет volumes обеих баз, Kafka и подготовленный граф OSRM. Используйте эту команду только когда локальные данные больше не нужны.

## Проверки Go-модулей

Проверки выполняются отдельно для каждого реализуемого модуля:

```bash
cd api
go test ./...
```

Та же команда запускается отдельно из `ingestion` и `bot`. Общего `go.mod` в корне намеренно нет.

## Настройки рейтинга и Mini App

Настройки Mini App и планировщика рейтинга подключены к конфигурации API:

| Параметр API | Значение / назначение |
| --- | --- |
| `RATING_RECALC_CRON` | `0 3 1 * *`: 1-го числа месяца в 03:00 Europe/Moscow; для недели — `0 3 * * 1` |
| `MAX_BOT_TOKEN` | Серверный токен MAX для проверки подписи Mini App; не BOT_SERVICE_TOKEN |
| `MINIAPP_INIT_DATA_MAX_AGE` | `1h`: допустимый возраст подписанных стартовых данных |
| `CORS_ALLOWED_ORIGIN` | Origin размещённого Mini App для CORS при разных origin |

Бот открывает настроенный в MAX URL Mini App. В production фронтенд собирается из `miniapp` и публикуется через Caddy по HTTPS. Для уведомлений сначала выполняется `/start`, регистрирующий личный чат; все действия с точками выполняются в Mini App. Планировщик предполагает один экземпляр API.

После реализации Kafka producer/consumer нужно проверить полный сценарий `/start` → Mini App → добавление точки → уведомление → текущий рейтинг и история → удаление. Отклонение неверных и просроченных initData уже покрыто unit-тестами API; проверки доступа к чужим точкам и полного сценария остаются интеграционной работой.
