# Рейтинг окружения точки

Алгоритм geo_logic_api_go перенесён в текущий API: формула калькулятора сохранена, а расстояния до инфраструктуры берутся из пешеходных маршрутов OSRM. Единица расчёта — TrackedLocation, без привязки к аренде. API синхронно рассчитывает рейтинг при `POST /api/v1/tracked-locations` и сохраняет каждый успешный результат в `rating_history`. Автоматический пересчёт по расписанию выполняется внутри API.

Результат сохраняется в rating_history и возвращается в ответе создания. Последнее значение и дата расчёта доступны в пользовательском списке точек, история — отдельным методом. Рейтинг не включается в уведомления. Создание и расчёт атомарны: общая ошибка OSRM или калькулятора возвращает `503 provider_unavailable` и не оставляет точку в БД.

## Подготовка признаков

1. В транзакции проверить пользователя и получить BusinessType с соответствующим InfraType конкурентов.
2. Через PostGIS предварительно выбрать InfraObject. Прямое расстояние используется только как грубый фильтр по MaxRadius и не попадает в формулу.
3. Запросить у OSRM пешеходные расстояния от новой точки до кандидатов. Координаты передаются в порядке lon,lat.
4. Пропустить отдельный объект с `NoRoute`; общую недоступность или некорректный ответ OSRM считать ошибкой операции.
5. По расстоянию OSRM исключить объекты за пределами MaxRadius их InfraType.
6. Сгруппировать объекты по InfraType и собрать InfraTypeFeatures: количество, минимум и среднее расстояний, сумму расстояний, количества в пределах 100/300/500 м и Influence.
7. IsCompetitor истинен, когда TypeID совпадает с BusinessType.InfraTypeID. Вес и радиус берутся из InfraType.
8. Передать LocationFeatures с BusinessTypeID калькулятору, атомарно сохранить точку и первую запись истории, вернуть рейтинг и время расчёта. Если подходящих объектов нет, калькулятор возвращает 5.0.

Рейтинг использует только постоянные InfraObject из БД API. Приватный кэш 2ГИС находится в отдельной БД ingestion и в расчёте не участвует. Полнота рейтинга зависит от загруженной инфраструктуры; загрузчик должен исключать дубли источников до upsert в API.

## Исходная формула

```text
influence = Σ max(0, 1 - distance/maxRadius)²
contribution = weight × log1p(influence)
raw = Σ positive_contributions - Σ competitor_contributions
rating = 10 / (1 + exp(-raw))
result = clamp(round(rating × 10) / 10, 0.1, 9.9)
```

Расстояние и MaxRadius — в метрах, weight и MaxRadius положительные. Для отрицательного raw сохраняется устойчивая ветвь старого кода: 10 × exp(raw) / (1 + exp(raw)).

Event не является отдельным слагаемым. События инициируют уведомления, но не вызывают пересчёт рейтинга. Причины и рекомендации описывают конкретное изменение отдельно от рейтинга.

5 — нейтральный результат, ниже 5 — преобладание конкурентного вклада, выше 5 — положительной инфраструктуры. Это вспомогательный показатель доступных данных, а не прогноз выручки. Нет отдельных коэффициентов сигнала и LOW/MEDIUM/HIGH. Просмотр рейтинга и истории доступен в Mini App; публичного endpoint ручного пересчёта нет.

## Плановый пересчёт и история

Планировщик работает внутри API и вызывает тот же сервис расчёта, используя актуальные InfraObject, веса и радиусы. `RATING_RECALC_CRON` — пятичастное cron-расписание; по умолчанию `0 3 1 * *` (1-го числа каждого месяца в 03:00), часовой пояс Europe/Moscow. Пример еженедельного запуска — `0 3 * * 1` (понедельник). Запуск происходит только по cron, без пересчёта при старте API.

Один экземпляр API выполняет планировщик; перекрывающийся запуск пропускается. Все точки обрабатываются последовательно, успешный результат каждой сохраняется отдельно, даже если значение не изменилось. Ошибка OSRM или калькулятора логируется без секретов и не останавливает остальные точки; прежний рейтинг и его время остаются доступны. Если точка удалена во время расчёта, запись не создаётся. Следующая попытка — по следующему расписанию, без восстановления пропущенных запусков и значений за прошлое время. При остановке API работа отменяется через context; API дожидается завершения задачи до закрытия БД.

`GET /api/v1/tracked-locations/{id}/rating-history?months=3` возвращает все сохранённые значения за выбранный период по возрастанию времени, без агрегации и интерполяции. `months` — положительное целое число, по умолчанию 3. Период включает обе границы: от момента запроса минус указанное число календарных месяцев до момента запроса. Правило календарного вычитания описано в [модели данных](data-model.md). Пустая история — `[]`; чужая и отсутствующая точка — `404`.

## Настройки и проверки

Значения Weight и MaxRadius загружаются ingestion в InfraType, конкретные значения ещё предстоит согласовать. Сопоставление рубрик 2ГИС типам инфраструктуры также требует настройки.

Сохранить тесты старого калькулятора: без признаков — 5; weight=2, influence=1 для положительной инфраструктуры — 8; для конкурента — 2; равные противоположные вклады — 5. Проверить агрегирование нескольких объектов, округление, границы, конечность результата и отмену context.

Интеграционные проверки должны подтверждать, что используется расстояние OSRM, кандидаты за MaxRadius и `NoRoute` исключаются, а недоступность OSRM возвращает `503 provider_unavailable` и откатывает создание точки.

Локальная подготовка пешеходного графа и примеры Route/Table API описаны в [инструкции OSRM](../osrm/README.md).

При реализации проверить атомарное сохранение точки и первого рейтинга, запись неизменившегося результата, период по умолчанию и пользовательский период (включая конец месяца), порядок истории, пустой результат, проверку владельца и каскадное удаление. Проверки планировщика: ежемесячный запуск в Europe/Moscow, запрет перекрытия, продолжение после ошибки отдельной точки и отсутствие записи при неудаче или удалении точки.
