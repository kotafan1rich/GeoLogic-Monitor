# Рейтинг окружения точки

API рассчитывает рейтинг при создании точки и по расписанию, используя инфраструктуру из своей БД и пешеходные расстояния OSRM. Формула нормализована по доступным категориям и не сравнивает точку с другими локациями. Это оценка окружения по загруженным данным, а не прогноз выручки.

## Конфигурация

Файл `api/rating.yml` содержит 40 категорий: вес `w`, радиус `R` в метрах и порог насыщения `k`. Здесь же заданы `beta=0.4`, `gamma=0.8`, `score_calibration=3.5`, шкала, границы, округление и лимит breakdown. Путь задаётся через `RATING_CONFIG_PATH` (по умолчанию `rating.yml` относительно рабочего каталога API). Файл включён в Docker-образ; для изменения без пересборки его можно смонтировать в контейнер. После изменения требуется перезапуск API.

`available_types` — явный список доступных датасетов. Поставляемый конфиг предполагает наличие всех 40 датасетов: перед развёртыванием список нужно сверить с фактически загруженными источниками. Тип без датасета исключается из числителя и знаменателя. Отсутствие объектов рядом не означает отсутствие датасета. Если весь список пуст, рейтинг равен 0.1, confidence — 0.

`profiles` задаёт множители релевантности по slug бизнеса, например:

```yaml
profiles:
  restaurant:
    hotel: 1.3
    pvz: 0
```

Пропущенный множитель равен 1. Чистая функция также принимает необязательный профиль, переопределяющий отдельные множители конфигурации, и `streetFactor` в диапазоне 0.85–1 (по умолчанию 1). HTTP эти параметры пока не принимает, в БД они не хранятся.

При запуске проверяются уникальность slug, ссылки на категории, конечность чисел, неотрицательные веса/релевантность, положительные радиусы и пороги, границы результата и коэффициентов. Неизвестные YAML-поля и несколько YAML-документов считаются ошибкой. Веса и радиусы в таблице `infra_types` сохраняют прежний контракт справочника, но новая формула их не использует.

## Подготовка данных

1. Получить BusinessType и slug прямых конкурентов.
2. Одним PostGIS-запросом выбрать инфраструктуру через `ST_DWithin` на geography в радиусе максимального `R` из YAML (800 м в поставляемом конфиге).
3. Запросить расстояния OSRM Table пакетами не более 99 целей; сохранить порядок ответов.
4. Пропустить объекты с отдельным `null` (маршрута нет). При общей ошибке OSRM прервать расчёт без сохранения частичного результата.
5. Передать slug бизнеса и пары «slug объекта — расстояние OSRM» в чистую функцию. Прямое расстояние используется только для пространственного отбора: ни Haversine, ни множитель DETOUR к формуле не применяются.
6. Добавить время расчёта в UTC вне чистой функции и сохранить итог в `rating_history`. Создание точки и первой записи истории атомарны; ошибка OSRM или калькулятора откатывает создание.

## Формула

Для каждого доступного типа:

```text
influence_t = Σ max(0, 1 − walkingDistance / R_t)²
sat_t = 1 − exp(−influence_t / k_t)
weight_t = w_t × relevance_t
```

Прямые конкуренты — только тот же slug, что и бизнес. Эта категория исключается из положительного числителя и знаменателя независимо от наличия конкурентов рядом. Заменители в первой версии не учитываются.

```text
positiveTypes = availableTypes без категории прямых конкурентов
score = Σ(weight_t × sat_t) / Σ(weight_t), t ∈ positiveTypes
score = 1 − exp(−score_calibration × score)
competitionPenalty = beta × sat_business
score *= (1 − competitionPenalty) × streetFactor
rating = clamp(round(scale × score^gamma × round_factor) / round_factor, min, max)
```

Если конкурентный датасет недоступен, штраф равен 0; это не подтверждает отсутствие конкурентов. При нулевом положительном знаменателе результат — минимальный рейтинг и confidence=0. Без объектов результат равен 0.1. Добавление положительного объекта не понижает рейтинг, добавление прямого конкурента не повышает его при неизменной конфигурации.

`confidence` — отношение доступного положительного веса к полному положительному весу профиля. Категория бизнеса исключается из обеих сумм. Это покрытие категорий, не статистическая достоверность и не показатель полноты конкурентного датасета.

Чистая функция возвращает `RatingAssessment`: rating, confidence, competitionPenalty и до пяти положительных вкладов breakdown. Вклад — `weight × sat / denominator` до общего штрафа. Сортировка по убыванию вклада, при равенстве — по slug. При одинаковых входных данных результат детерминирован; функция не использует часы, БД или сеть.

Публичные HTTP DTO не изменены. В историю сохраняются только рейтинг и время; дополнительные показатели доступны внутри расчёта. Данные кэша 2ГИС из ingestion в рейтинг не входят. Event инициирует уведомления, но не является слагаемым рейтинга.

## Плановый пересчёт и история

Планировщик работает внутри API и вызывает тот же сервис расчёта, используя актуальные InfraObject, веса и радиусы. `RATING_RECALC_CRON` — пятичастное cron-расписание; по умолчанию `0 3 1 * *` (1-го числа каждого месяца в 03:00), часовой пояс Europe/Moscow. Пример еженедельного запуска — `0 3 * * 1` (понедельник). Запуск происходит только по cron, без пересчёта при старте API.

Один экземпляр API выполняет планировщик; перекрывающийся запуск пропускается. Все точки обрабатываются последовательно, успешный результат каждой сохраняется отдельно, даже если значение не изменилось. Ошибка OSRM или калькулятора логируется без секретов и не останавливает остальные точки; прежний рейтинг и его время остаются доступны. Если точка удалена во время расчёта, запись не создаётся. Следующая попытка — по следующему расписанию, без восстановления пропущенных запусков и значений за прошлое время. При остановке API работа отменяется через context; API дожидается завершения задачи до закрытия БД.

`GET /api/v1/tracked-locations/{id}/rating-history?months=3` возвращает все сохранённые значения за выбранный период по возрастанию времени, без агрегации и интерполяции. `months` — положительное целое число, по умолчанию 3. Период включает обе границы: от момента запроса минус указанное число календарных месяцев до момента запроса. Правило календарного вычитания описано в [модели данных](data-model.md). Пустая история — `[]`; чужая и отсутствующая точка — `404`.

## Проверки и переход

Тесты проверяют пустое окружение, влияние расстояния до метро, монотонность, насыщение кафе, штраф конкурентов, недоступные категории, профиль, streetFactor, нулевые веса, радиусы, границы, порядок breakdown, детерминизм и отмену context. Сервисные проверки контролируют одну выборку, передачу расстояний OSRM, пропуск NoRoute, отказ провайдера и сохранение истории. Отдельно проверяются разбиение OSRM на пакеты и сохранение порядка.

Benchmark чистой функции на 1 000 объектах и 40 категориях:

```bash
cd api
go test ./internal/service/calculate -run '^$' -bench BenchmarkFormulaCalculator1000Objects -benchmem
```

Цель — менее 5 мс на точку без SQL и OSRM. История не переписывается: новая формула применяется при создании точки и очередном штатном пересчёте. Старые и новые значения используют разные модели и могут иметь скачок на границе перехода.
