# GeoLogic Monitor Bot

Bot связывает GeoLogic Monitor с MAX. Он принимает webhook-обновления, регистрирует личный чат пользователя в API и отправляет в MAX уведомления, полученные из Kafka.

Управление точками и просмотр рейтинга выполняются в Mini App. Bot не хранит продуктовые данные и не обращается к PostgreSQL напрямую.

## Место в системе

```text
MAX ── webhook /start ──→ Bot ── регистрация чата ──→ API
 ↑                         ↑
 └──── сообщения MAX ──────┴──── задания Kafka ←──── ingestion
```

[Контейнерная диаграмма системы](../docs/diagrams/rendered/c4-containers.svg)

## Возможности

- регистрация webhook в MAX при старте;
- обработка событий `bot_started` и команды `/start`;
- создание или обновление пользователя и его личного чата через API;
- отправка приветственного сообщения после регистрации;
- чтение заданий на уведомления из Kafka;
- формирование сообщений о новом конкуренте или предстоящем мероприятии;
- повтор отправки при временной ошибке и ручное подтверждение Kafka offset.

## Быстрый запуск

Подготовьте `bot/.env`, запустите API и Kafka, затем откройте публичный HTTPS-туннель к порту бота:

```bash
cp bot/.env.template bot/.env
docker compose up -d api kafka
task bot:tunel
```

Укажите выданный туннелем адрес с путём `/webhook` в `WEBHOOK_URL`, настройте токены и запустите сервис:

```bash
task bot:up
docker compose logs -f bot
```

Для запуска без Docker нужны доступные API и Kafka, публичный HTTPS webhook и рабочий каталог `bot`:

```bash
cd bot
KAFKA_BROKERS=localhost:9092 go run ./cmd/bot
```

Подробная настройка окружения и порядок запуска описаны в [инструкции по разработке](docs/development.md).

## Текущее состояние и ограничения

- Webhook MAX, сценарий `/start`, Kafka consumer и отправка сообщений реализованы.
- Producer уведомлений в `ingestion` отсутствует, поэтому сквозной сценарий доставки пока не завершён.
- Bot не предоставляет health endpoint и не хранит историю отправленных уведомлений.
- Kafka-сообщения обрабатываются последовательно; неисправимые события переносятся в DLQ, автоматического перезапуска consumer после инфраструктурной ошибки нет.
- При сбое между отправкой сообщения и commit offset возможна повторная доставка.
