# Архитектура Bot

Bot является транспортной границей между MAX, API и Kafka. Сервис принимает пользовательские события из MAX, регистрирует адресата уведомлений в API и доставляет подготовленные задания обратно в MAX.

[Контейнерная диаграмма](../../docs/diagrams/rendered/c4-containers.svg) · [OpenAPI](../../api/docs/openapi.yaml) · [AsyncAPI](../../docs/asyncapi/notifications.yaml)

## Ответственность и границы

Bot отвечает за webhook MAX, сценарий `/start`, чтение Kafka и представление уведомлений в виде сообщений. Создание точек и расчёт рейтинга принадлежат API и Mini App, а обнаружение изменений — `ingestion`.

Собственной базы данных у Bot нет. Пользователь и личный чат сохраняются через HTTP API, а Kafka используется только как входная очередь заданий на доставку.

## Слои

```text
cmd/bot → app/ручной DI → HTTP и Kafka handlers → services → repositories
                                                               ├── API
                                                               └── MAX
                              Kafka consumer ←──────────────── Kafka
```

- `cmd/bot` загружает конфигурацию, создаёт приложение и запускает его.
- `internal/app` вручную собирает зависимости, HTTP-сервер и Kafka consumer.
- `internal/handler/http` принимает webhook через официальный MAX SDK.
- `internal/handler/bot` выбирает обработчик для события `bot_started` или команды `/start`.
- `internal/handler/kafka` декодирует транспортное DTO и передаёт уведомление сервису.
- `internal/service` реализует регистрацию пользователя и форматирование уведомлений.
- `internal/repository` и `internal/integrations` изолируют MAX, API и Kafka от прикладной логики.
- `internal/domain` не зависит от форматов HTTP- и Kafka-контрактов.

Ручной DI сохраняет зависимости явными и соответствует устройству остальных Go-сервисов проекта.

## Поток регистрации

1. При старте Bot регистрирует в MAX `WEBHOOK_URL` для событий `message_created` и `bot_started`.
2. MAX отправляет обновление на `POST /webhook` с общим webhook-секретом.
3. Dispatcher обрабатывает запуск бота или сообщение с командой `/start`; остальные сообщения игнорируются.
4. Сервис передаёт MAX user ID и chat ID в `PUT /api/v1/users/me` с сервисным Bearer-токеном.
5. После успешного ответа API Bot отправляет в этот чат приветственное сообщение.

Повторный `/start` выполняет тот же idempotent upsert в API и снова отправляет приветствие. Полный HTTP-контракт регистрации определён в [OpenAPI](../../api/docs/openapi.yaml).

## Поток уведомления

1. Consumer читает одно сообщение из настроенного Kafka topic.
2. Handler декодирует JSON и преобразует транспортное DTO в domain-модель.
3. Сервис выбирает шаблон по типу уведомления и формирует текст.
4. Repository отправляет сообщение в MAX по `max_chat_id`.
5. Consumer подтверждает offset только после успешной обработки.

Повторные попытки, терминальные ошибки и ограничения доставки описаны в [документе об уведомлениях](notifications.md). Структура сообщения определяется [AsyncAPI](../../docs/asyncapi/notifications.yaml).

## Запуск и остановка

При запуске сервис поднимает HTTP-сервер, параллельно регистрирует webhook MAX и создаёт Kafka consumer. Ошибка регистрации webhook завершает приложение. Ошибка создания consumer записывается в журнал, но HTTP-сервер продолжает работать; ошибка уже запущенного consumer останавливает только consumer и также записывается в журнал.

При `SIGINT` или `SIGTERM` общий context отменяется, consumer закрывается, а HTTP-сервер получает до 10 секунд на graceful shutdown.

## Решения и ограничения

- Bot не владеет постоянными данными и не зависит от схемы БД API.
- HTTP DTO, Kafka DTO и domain-модели разделены, чтобы внешние форматы не распространялись на сервисный слой.
- Текст уведомления формируется в Bot: Kafka содержит данные для доставки, а не готовый текст MAX.
- Уведомления обрабатываются по одному; параллельной доставки внутри экземпляра нет.
- Встроенного health endpoint, DLQ, истории уведомлений и автоматического перезапуска consumer нет.
- Producer в `ingestion` ещё не реализован, поэтому полный путь от обнаружения изменения до сообщения MAX недоступен.
