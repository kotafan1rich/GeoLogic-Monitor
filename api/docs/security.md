# Авторизация и безопасность API

API обслуживает три независимые доверительные зоны. Для каждой используется отдельная схема авторизации; токены не взаимозаменяемы.

| Клиент | Маршруты | Авторизация |
| --- | --- | --- |
| MAX Mini App | Пользовательские `/api/v1` | `X-Max-Init-Data` с подписанным `window.WebApp.initData` |
| `bot` | Регистрация пользователя и чата | `Authorization: Bearer <BOT_SERVICE_TOKEN>` и `X-Max-User-Id` |
| `ingestion` | `/internal/v1` | `Authorization: Bearer <INGESTION_SERVICE_TOKEN>` |

Полное соответствие схем маршрутам задаёт [OpenAPI](openapi.yaml).

## MAX Mini App

Mini App передаёт исходную строку `window.WebApp.initData` без разбора и повторного кодирования:

```http
X-Max-Init-Data: <raw initData>
```

API:

1. разбирает URL-кодированные пары и отклоняет пустые, повреждённые и повторяющиеся параметры;
2. извлекает единственный `hash`;
3. сортирует остальные параметры и собирает подписываемую строку;
4. выводит секретный ключ через HMAC-SHA256 от `MAX_BOT_TOKEN` с ключом `WebAppData`;
5. вычисляет и сравнивает подпись безопасным сравнением;
6. проверяет положительный `auth_date`, запрет даты из будущего и `MINIAPP_INIT_DATA_MAX_AGE`;
7. принимает положительный `user.id` только после успешной проверки.

Проверенный MAX user ID помещается в context запроса. Handler находит внутреннего пользователя и проверяет владение точками. `initDataUnsafe` пригоден для отображения, но не является доказательством личности.

Такой механизм связывает пользователя со всеми подписанными параметрами запуска и не требует передавать постоянный секрет в браузер.

## Доступ bot

`bot` регистрирует пользователя и личный чат через `PUT /api/v1/users/me`. Bearer-токен доказывает, что запрос пришёл от bot-сервиса; `X-Max-User-Id` передаёт идентификатор из уже проверенного обновления MAX.

Сам по себе `X-Max-User-Id` не авторизует запрос. `BOT_SERVICE_TOKEN` не используется Mini App и не открывает внутренние маршруты ingestion.

## Доступ ingestion

Все методы `/internal/v1` защищены отдельным `INGESTION_SERVICE_TOKEN`. Они предназначены для загрузки справочников, инфраструктуры и событий, чтения точек для мониторинга и запроса маршрутов.

Разделение токенов ограничивает последствия утечки: один сервис не получает полномочия другого и не может выдавать себя за пользователя Mini App.

## CORS и транспорт

API разрешает браузерные запросы только для `CORS_ALLOWED_ORIGIN`. В production Mini App и API должны работать по HTTPS. CORS не заменяет авторизацию: каждый пользовательский запрос всё равно обязан содержать валидные initData.

`/health` и Swagger UI публичны. Схемы авторизации и примеры запросов документируются в OpenAPI, но значения секретов туда не помещаются.

## Секреты и журналирование

- реальные токены и ключ DaData задаются окружением и не коммитятся;
- `MAX_BOT_TOKEN`, `BOT_SERVICE_TOKEN` и `INGESTION_SERVICE_TOKEN` должны различаться;
- исходные initData, подписи и токены не логируются;
- клиенту возвращается общий `401 Unauthorized` без раскрытия причины проверки подписи;
- при сравнении служебных токенов используется constant-time comparison.
