# Архитектура API

API объединяет HTTP-границу продукта, постоянное хранилище и расчёт рейтинга. Сервис остаётся отдельным Go-модулем и не импортирует код `bot` или `ingestion`.

[Компонентная диаграмма](../../docs/diagrams/rendered/c4-components.svg) · [OpenAPI](openapi.yaml)

## Ответственность и границы

API отвечает за пользователей MAX, точки, справочники, инфраструктуру, события, геокодирование, пешеходные расстояния, расчёт и историю рейтинга.

`ingestion` загружает данные только через внутренние методы API. `bot` регистрирует чат через служебный метод. Mini App вызывает пользовательские методы напрямую. Такое владение не позволяет соседним сервисам обходить бизнес-правила или зависеть от миграций API.

## Слои

```text
cmd/api → app/DI → HTTP handler → service → repository → PostgreSQL / DaData / OSRM
                                      ↓
                                    domain
```

- `cmd/api` загружает конфигурацию и запускает приложение.
- `internal/app` применяет миграции, вручную собирает зависимости, запускает HTTP-сервер и планировщик.
- `internal/handler` преобразует HTTP DTO и ошибки, не содержит SQL и расчётной логики.
- `internal/service` реализует сценарии и работает с репозиториями через интерфейсы.
- `internal/repository` изолирует SQL и внешние HTTP-клиенты.
- `internal/domain` не зависит от HTTP, pgx и формата внешних ответов.

Ручной DI сохраняет граф зависимостей явным и достаточен для размера сервиса; отдельный DI-фреймворк не добавляется.

## Основные потоки

### Создание точки

1. Middleware проверяет MAX initData и помещает `user.id` в context.
2. Handler валидирует запрос и передаёт его сервису.
3. Сервис получает пользователя и тип бизнеса, выбирает инфраструктуру рядом через PostGIS.
4. OSRM уточняет пешеходные расстояния до кандидатов.
5. Чистый калькулятор рассчитывает рейтинг.
6. Точка и первая запись `rating_history` сохраняются одной транзакцией.

Расчёт выполняется до фиксации транзакции: недоступность OSRM или ошибка формулы не оставляет точку без первого результата.

### Загрузка данных

`ingestion` выполняет идемпотентные upsert справочников, объектов и событий через `/internal/v1`. Постоянная запись находится в API, поэтому расчёт рейтинга и пользовательская выдача используют единый источник истины.

### Плановый пересчёт

Планировщик использует ту же цепочку выбора инфраструктуры, OSRM и калькулятора. Он работает в `Europe/Moscow`, запускается по `RATING_RECALC_CRON` и не выполняет catch-up при старте. Перекрывающийся запуск пропускается, точки обрабатываются последовательно.

Каждый успешный расчёт добавляет новую запись истории. Ошибка отдельной точки сохраняет прежнее значение и не останавливает остальные расчёты. Планировщик рассчитан на единственный экземпляр API.

## Интеграции

| Зависимость | Назначение | Поведение при ошибке |
| --- | --- | --- |
| PostgreSQL + PostGIS | Постоянные данные, транзакции и пространственный отбор | Ошибка запуска или операции возвращается вызывающему сценарию |
| DaData Suggest | Подсказки адресов и обратное геокодирование | API возвращает ошибку внешнего провайдера |
| OSRM Table | Пешеходные расстояния для рейтинга и ingestion | Общая ошибка прерывает пакет; отдельный `null` означает отсутствие маршрута |

OSRM вызывается только из API. Это не дублирует маршрутизацию и её конфигурацию в `ingestion`, а внутренний метод возвращает одинаковую семантику расстояний всем потребителям.

## Запуск и остановка

При старте сервис загружает и валидирует env-конфигурацию и `rating.yml`, подключается к БД, применяет goose-миграции, создаёт HTTP-сервер и планировщик. `/health` подтверждает работу HTTP-процесса, но не проверяет внешние провайдеры.

При `SIGINT` или `SIGTERM` планировщик отменяет текущую работу, HTTP-сервер получает до 10 секунд на graceful shutdown, после чего закрывается пул БД.

## Решения и ограничения

- Постоянные данные принадлежат API, а не разделяются между сервисами напрямую.
- DTO транспорта и модели БД отделены от domain-моделей, чтобы изменения внешних форматов не распространялись на бизнес-логику.
- Рейтинг хранится как журнал успешных измерений: это даёт историю без отдельного текущего значения и сохраняет результаты старых формул.
- Транзакции ограничены базой API, межсервисный обмен использует идемпотентные HTTP-операции и Kafka, а планировщик выполняется в единственном экземпляре API.
