# Архитектура Mini App

Mini App является браузерной границей GeoLogic Monitor внутри MAX. Приложение показывает пользовательские сценарии, получает данные запуска от MAX Web App SDK и вызывает API, но не содержит серверной бизнес-логики и не владеет постоянными данными.

[Контейнерная диаграмма](../../docs/diagrams/rendered/c4-containers.svg) · [OpenAPI](../../api/docs/openapi.yaml)

## Ответственность и границы

Mini App отвечает за навигацию между экранами, ввод и подтверждение данных точки, запрос геолокации устройства, отображение рейтинга и обработку состояний интерфейса.

API отвечает за проверку MAX `initData`, регистрацию пользователя, геокодирование, хранение точек, расчёт Smart Score и историю рейтинга. Mini App не обращается к PostgreSQL, DaData или OSRM напрямую и не повторяет правила расчёта на клиенте.

## Структура клиента

```text
main.tsx → App.tsx → screens → api.ts → /api/v1 → API
                 ├── useRatingHistory.ts
                 ├── rating.ts
                 └── components/ScoreChart.tsx

max.ts → window.WebApp.initData ───────────────┘
```

- `main.tsx` создаёт React-приложение в строгом режиме.
- `App.tsx` хранит текущий экран, загруженные справочники и точки, черновик формы и состояние мутаций.
- `screens` разделяют пользовательские сценарии, но не вызывают внешние сервисы в обход общего API-клиента.
- `api.ts` добавляет авторизационный заголовок, ограничивает запрос 30 секундами и преобразует HTTP-ошибки в единое клиентское представление.
- `useRatingHistory.ts` изолирует загрузку и повторный запрос истории.
- `rating.ts` содержит только форматирование дат и вычисление изменения между двумя последними значениями.
- `ScoreChart.tsx` строит доступный SVG-график по уже рассчитанным API значениям.

Отдельный router не используется: у приложения небольшой линейный сценарий, поэтому текущий экран хранится в React state. Это упрощает MVP, но не даёт глубоких ссылок и восстановления экрана после обновления страницы.

## Запуск и авторизация

1. Страница загружает MAX Web App SDK с `https://st.max.ru/js/max-web-app.js`.
2. SDK предоставляет сырую строку `window.WebApp.initData`.
3. При отсутствии строки Mini App не делает запросов и показывает инструкцию открыть приложение через MAX.
4. API-клиент добавляет `X-Max-Init-Data` к каждому запросу `/api/v1`.
5. API проверяет подпись, срок действия и пользователя; Mini App не пытается доверять или разбирать `initData` самостоятельно.
6. Любой ответ `401` переводит интерфейс на экран истёкшей сессии.

Подробные границы доверия описаны в [документе по безопасности](security.md).

## Основные пользовательские потоки

### Загрузка точек

После авторизованного запуска приложение параллельно загружает типы бизнеса и точки пользователя. Список точек содержит текущий рейтинг, а история каждой показанной точки запрашивается отдельно, чтобы вывести изменение с предыдущего расчёта.

Экран деталей повторно получает историю и показывает SVG-график, значения и время расчёта в часовом поясе `Europe/Moscow`. Период запроса фиксирован параметром `months=3`.

### Добавление точки

1. Пользователь вводит название и выбирает загруженную из API категорию.
2. Адрес выбирается из подсказок API после задержки 350 мс либо определяется через браузерную геолокацию и обратное геокодирование.
3. Ручной текст адреса не считается выбранным адресом: продолжить можно только после получения адреса с координатами.
4. Перед запросом приложение показывает экран подтверждения.
5. API создаёт точку и рассчитывает первый Smart Score; Mini App добавляет успешный ответ в локальный список и открывает детали.

На время создания повторная мутация блокируется. При сетевой или неопределённой серверной ошибке интерфейс советует проверить список точек перед повтором, поскольку клиент не может установить, был ли запрос сохранён.

### Удаление точки

Удаление запускается только после подтверждения в диалоге. После ответа `204` точка удаляется из локального списка. Ответ `404` трактуется как уже достигнутый результат: приложение сообщает, что точка недоступна, и обновляет список.

## Работа с состоянием и ошибками

Для загружаемых данных используется явное состояние `loading`, `success` или `error`. Независимые операции имеют собственные кнопки повтора. При переходе между экранами незавершённые запросы чтения отменяются через `AbortController`.

Черновик формы, список точек и навигация находятся только в памяти React. Браузерные хранилища, cookies и клиентский кэш данных не используются; `fetch` вызывается с `cache: no-store` и `credentials: omit`.

## Публикация

Production-сборка создаётся TypeScript и Vite, затем раздаётся Nginx. Правило `try_files` возвращает `index.html` для клиентского приложения, а `/api/` проксируется в контейнер `api:8080`.

В общем Compose Caddy также публикует Mini App и API на одном origin: интерфейс обслуживается с `/`, API — с `/api/*`. Клиент использует только относительные URL, поэтому адрес backend не встраивается в production bundle.

## Решения и ограничения

- API остаётся единственным источником продуктовых данных и правил рейтинга.
- Сырые MAX `initData` передаются API без клиентского разбора, поскольку браузеру нельзя доверить проверку подписи.
- Same-origin proxy исключает необходимость хранить адрес API или сервисный токен в клиентской сборке.
- Локальный список обновляется только после успешного ответа API; удаление также подтверждается сервером до изменения списка.
- Состояние не сохраняется между перезагрузками и не синхронизируется между вкладками.
- История списка загружается отдельным запросом для каждой точки; пакетного endpoint и клиентской пагинации нет.
- Service Worker, offline-режим и собственная аналитика не реализованы.
