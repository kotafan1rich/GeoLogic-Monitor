# Правила работы AI-агентов

## Главные ограничения

- Выполняй только явно поставленную задачу.
- Не исправляй ошибки, не рефактори и не форматируй код, который не относится к задаче.
- Не изменяй существующую структуру проекта без прямого запроса.
- Не переименовывай и не перемещай существующие файлы, каталоги, пакеты и сервисы без необходимости, указанной в задаче.
- Новые модули, пакеты и компоненты делай максимально похожими на уже существующие: повторяй их структуру, именование, способы конфигурации и подключения зависимостей.
- Не придумывай сложную архитектуру сверх того, что требуется задачей. Выбирай самое простое решение, совместимое с текущим проектом.
- Не добавляй зависимости, абстракции, универсальные фреймворки или инфраструктуру «на будущее».
- Если выполнение задачи требует изменения архитектуры, контрактов или структуры проекта, сначала сообщи об этом и уточни решение.

## Границы проекта

- Проект состоит из трёх независимых Go-модулей: `api`, `ingestion` и `bot`.
- У каждого модуля собственный `go.mod`, конфигурация и `Dockerfile`.
- Не создавай общий Go-модуль и не добавляй прямые импорты между соседними модулями.
- `api` владеет постоянными данными и миграциями.
- `ingestion` получает и передаёт постоянные данные через внутренний API; собственная БД используется только для его кэша.
- `bot` работает через HTTP API и Kafka и не обращается к базе данных напрямую.
- Соблюдай существующее направление зависимостей: `cmd -> app/DI -> handler -> service -> repository`.
- Используй ручную сборку зависимостей. Не добавляй DI-фреймворк без отдельного запроса.

## Контракты и безопасность

- При изменении HTTP-контракта обновляй OpenAPI и обе локальные копии связанных DTO.
- При изменении Kafka-сообщений обновляй AsyncAPI и producer/consumer в рамках той же задачи.
- Не добавляй секреты и реальные значения окружения в репозиторий.
- Не логируй токены, пароли и сырые ответы внешних сервисов, если они могут содержать чувствительные данные.

## Работа с изменениями

- Перед правками изучи соседние файлы и следуй их стилю.
- Сохраняй пользовательские изменения и не перезаписывай несвязанные правки.
- Ограничивай diff файлами и строками, необходимыми для задачи.
- Для Go-кода запускай форматирование только изменённых файлов.
- Не пиши избыточное количество тестов. Добавляй только основные тесты для критичного и изменённого поведения, без дублирующих сценариев и попытки покрыть все возможные комбинации.
- Выполняй проверки, относящиеся к изменённому модулю. Не исправляй найденные посторонние проблемы без запроса.
- Если проверка невозможна из-за отсутствующих сервисов, переменных окружения или инструментов, явно укажи это в результате.
- Соблюдай процесс работы с ветками и Pull Request из `CONTRIBUTING.md`.
